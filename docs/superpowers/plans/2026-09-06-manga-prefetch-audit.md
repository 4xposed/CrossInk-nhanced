## Findings that determine the integration

- CrossInk foreground decoding combines image geometry, source fingerprint, cache publication and renderer access in `src/activities/reader/MangaReaderActivity.cpp:499`. Reusable geometry already exists in `lib/MangaPanel/MangaImageGeometry.h:20`. Snapshot both base and rotated viewports (including bezel insets) under RenderLock; merely swapping width/height cannot reproduce asymmetric insets. Both foreground and worker should consume the same pure geometry/identity builder.
- `ImageToFramebufferDecoder.h:15` has no cache-only or cancellation fields. JPEG and PNG unconditionally read renderer dimensions at `JpegToFramebufferConverter.cpp:400` and `PngToFramebufferConverter.cpp:343`; PNG initializes a framebuffer writer at `:243`, and JPEG has equivalent writer calls. A background call to the current public method is unsafe.
- Existing streamed cache memory is bounded: `PixelCache.h:58` caps the band at 24 KiB, plus one packed row (`:90`); it does not allocate an entire image. Its nominal one-row PNG request still allocates at least 16 rows. PNG also needs its decoder and a source-width gray row (`PngToFramebufferConverter.cpp:336`, `:420`). Do not promise a one-row total allocation.
- Decoder success currently permits cache startup failure and ignores `finalize()` failure (`JpegToFramebufferConverter.cpp:497`, `:520`; PNG `:435`, `:459`). That is a valid foreground fallback but an invalid cache-only success contract. `PixelCache.h:158` also ignores close failure. Cache-only completion must require a successful stream, sync/close, and complete decode.
- `MangaPixelCache.cpp:172` gives foreground and worker the same `.tmp` filename. `:213` publishes raw pixels and a checksummed identity sidecar by two renames after removing the old pair. This is recoverable validation, not a single atomic transaction. Never run two writers or a reader and publisher for this asset concurrently. `sourceIdentity()` alone does not validate the payload (`:154`); warming must use `configure()` plus `open()` for a hit.
- `fingerprintImage()` reads the entire source, and cache open/publication checksum the payload (`MangaPixelCache.cpp:114`, `:134`, `:193`, `:213`). Cancellation only in decoder draw callbacks leaves potentially long uninterruptible phases. Add optional cancellation to these chunk loops and check before source/header opens and publication. During the final pair replacement, finish the short transaction or clean it up before acknowledging cancellation.
- HAL storage locking protects individual operations (`lib/hal/HalStorage.cpp:301`, `:409`), not the lifetime between open and close. It cannot prevent concurrent readers of the same source. `RenderLock::peek()` (`ActivityManager.cpp:818`) is an observation, not ownership; a render can start immediately after a worker checks it. Do not transplant that as the coordination guarantee.
- Reader exit saves progress/stats before releasing resources (`MangaReaderActivity.cpp:107`). Join the worker before those operations. ActivityManager push deliberately does **not** call onExit (`ActivityManager.cpp:297`); child lookup/settings/frontlight and sleep flows require quiescence as well. An exit-only implementation leaves a worker active behind another screen.

## Pinned Matcha behavior and defect to avoid

Reference paths below are relative to `/Users/daniel/code/matcha-reader`.

`MangaReaderActivity.h:184` documents a one-slot job/result handshake, copied paths and dimensions, generation stamps, cache-only worker and join-before-teardown. Its dwell is 150 ms for first panel and 400 ms for next page/panel (`MangaReaderActivity.cpp:45`); its worker uses an 8192-byte stack (`:61`). These are useful starting policies, not CrossInk timing or memory measurements.

The claimed cancellation bound is false for JPEG: `lib/Epub/Epub/converters/JpegToFramebufferConverter.cpp:148` ignores a true cancel callback once two-thirds of cached rows are flushed. That callback includes exit (`MangaReaderActivity.cpp:1141`), so even exit can continue decoding the remainder. Do not port this exception. Every explicit cancellation must abort regardless of progress.

JPEG callback early-exit needs a separate `cancelled` flag: local installed JPEGDEC assigns callback return to `bContinue` (`.pio/libdeps/default/JPEGDEC/src/jpeg.inl:5335`) but returns success from `iErr == 0` (`:5366`). PNG returns `PNG_QUIT_EARLY` (`.pio/libdeps/default/PNGdec/src/png.inl:934`). Track cancellation explicitly for both so incomplete output cannot be finalized as a valid cache.

## Minimal implementation proposal

1. Add a renderer-free cache decode entry point to the existing decoder interface, retaining the foreground wrapper. Share the same internal decode routine with an optional renderer pointer; the cache entry supplies exact output geometry, screen extents and cancellation callback/context. A valid cache-only call must never initialize DirectPixelWriter, read orientation/framebuffer state, or invoke renderer methods. Keep the same dither origin and scale calculations so cold, foreground-generated and prefetched pixels match. Default cancellation remains absent for existing callers.
2. Add callback checks before decode setup, per JPEG MCU/PNG scanline, after decode, and in source/payload checksum loops. On cancellation, abort the stream and close all files before reporting completion. Cache-only stream allocation/write/finalization failure returns failure; foreground still renders without caching. No finish-nearly-done exception.
3. Add one activity-owned worker, one pre-reserved copied path/config slot and one small result slot. No queue/vector of images and no borrowed MangaBook page bytes. Use explicit atomics with release/acquire handoff: idle -> posted/running -> result-ready -> idle. The owner never rewrites a running slot; cancellation invalidates generation, and a new job waits until the old result is consumed. Worker never takes RenderLock and never applies results to reader state.
4. Give speculative work an explicit ownership gate, rather than relying on peek(). Foreground intent revokes further jobs and sets cancellation **before** beginning manga file operations. While a job is still active, retain the pending navigation/menu/render action and return to polling input; do not wait for an entire decode in loop(). Worker releases the gate only after closing its source/cache handles and freeing decode scratch. The next loop can then load the page/render/save. Render-task entry must also revoke/check the gate before any cache access; it can defer the render until completion notification triggers a new request. Coalesce desired navigation rather than dropping button edges during cancellation.
5. Apply this quiescence contract to page/panel movement, rotation, settings, manual refresh, progress/stats flushes, child pushes and sleep/exit. A small default no-op activity lifecycle readiness hook, checked by ActivityManager before Push/Replace/Pop, is safer than patching only manga menu call sites: global frontlight and alert pushes otherwise escape the contract. Keep pending transitions pending while the hook cancels and reports not-ready. Worker has no dependency on the hook's RenderLock. Terminal onExit still cancels, wakes and joins defensively before freeing owned state; do not force-delete a task with live files or free its context on a timeout. Audit sleep code that saves or snapshots before the pending transition, too.
6. Preserve HAL locking for each operation. Do not hold StorageLock around a decoder: its nested HAL calls would acquire the same nonrecursive mutex. The manga ownership gate prevents same-asset opens and overlapping foreground decoder allocations; per-call HAL locking handles other routine SD calls. If interpreting the repo's stricter one-reader-at-a-time rule literally across unrelated files, extend the ownership handoff to those readers before enabling the worker; do not claim per-call locking alone proves that stronger contract. Check this on real hardware, whose constraint is stronger than the simulator.
7. After a successful render and the idle dwell, prioritize the first existing crop when panel use is relevant; in panel view warm the next available panel, and warm the next overview when useful. Skip absent assets, already validated caches, and unsupported/nonbeneficial formats (BMP can initially be skipped, matching upstream). Prepare copied candidate paths only while worker-idle; worker performs header/fingerprint/decode I/O. Never mutate foreground MangaBook's borrowed page data to inspect a speculative next page. Use canonical path resolution or a separately bounded worker lookup if fallback discovery is required. Skip/retry on OOM with a dwell/backoff, not every loop tick.
8. With exclusive manga producer ownership, reuse the existing `.tmp`/sidecar publication instead of adding an alternate cache format. Cancelled/stale work cannot publish; check generation before publication. Consume results under RenderLock, applying only matching generation/geometry/settings; a completed job reports warmed/skipped/failed/cancelled, not a shared decoder or open file. Stale completed cache data remains disposable and must still pass identity validation on use.

## Memory and verification gates

No second framebuffer, framebuffer snapshot, PSRAM requirement or full-image pixel buffer is needed. Owned path/config/result storage is session-sized; decoder/band scratch is job-scoped and fully released before foreground decode. Use fallible ownership helpers for new allocations. Task creation failure disables warming and preserves ordinary reading. Do not copy Matcha's 60000-byte floor without computing decoder + band + row + stack + required internal-RAM reserve, and check largest allocatable block as well as free heap (`lib/MemoryBudget/MemoryBudget.h:171`). An 8192-byte stack is a conservative upstream starting point, requiring CrossInk high-water measurement; do not place a large cache object/path array on a small worker stack without accounting for it.

Meaningful automated checks: one-slot ownership and stale result rejection; cancellation before start/during checksum/early-middle-final JPEG blocks and PNG scanlines; cancellation after the two-thirds threshold; no renderer access in cache-only mode; byte-identical foreground/cache-only output and identity across orientations/insets; startup/write/sync/close/rename failure cleanup; no same-asset overlap; pending navigation is retained; worker quiesces on push/replace/sleep/exit; no old worker survives repeated opens. Existing simulator JPEG/PNG stubs cannot certify real image paths. Use real decoder host tests where practical and physical decoding for final acceptance.

Hardware: on X3/X4 C3, open a JPEG/PNG manga with several panels, pause to warm then enter the next panel/page, rapidly reverse/rotate, open lookup/menu/frontlight, exit and sleep while a large image is warming. Expect responsive button polling, explicit cancellation and cache-hit logs, no partial valid cache, no duplicate open failures, and identical geometry/grayscale on cold and warm images. Record free internal heap, max allocation and task stack high-water before/after repeated cycles; repeat on Sticky/X4 Pro with PSRAM metrics. Clear only the relevant disposable `/.crosspoint/manga_<folder-crc>/` pixel cache for cold comparisons. No build, timing, heap or hardware pass is claimed by this report.
