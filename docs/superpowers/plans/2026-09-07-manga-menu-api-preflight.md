# Manga menu API preflight (Task 10e)

Date: 2026-09-07. This is a read-only preflight of the Task 10e brief and `2026-09-06-manga-menu-completion-audit.md`. CodeGraph was consulted before the targeted source reads. No source, test, build, simulator, serial, SDK, commit, or push operation was performed.

## OptionPopup can present all 16 rows

There is no fixed row ceiling in `OptionPopup`. Every `show()` overload copies all supplied labels into `ownedStrings` (`src/components/OptionPopup.h:29-69`), and `activate()` clamps selection against that full count (`:410-431`). Both drawing and touch hit testing derive a runtime window from screen height, UI scale, theme padding, title wrapping, and row height. The window has at least one row, is centered around the selected row, and retains a scrollbar gutter whenever rows are hidden (`OptionPopup.h:285-346`; `src/components/themes/BaseTheme.cpp:1121-1208`). Draw and hit-test use the same `visibleStart`/visible-count calculation, and touch indexes add `firstOptionIndex` (`OptionPopup.h:122-173`, `:355-383`). Thus a 16-row manga menu does not require tabs or a replacement widget.

The number visible at once is intentionally not constant. Portrait has 800 logical pixels of height and landscape 480, while the themes use different vertical padding and spacing: base 16/4/6, Lyra 20/12/8, and RoundedRaff 24/10/6 for inner padding/selection vertical padding/item spacing (`src/components/themes/BaseTheme.h:183-218`; `src/components/themes/lyra/LyraTheme.h:50-85`; `src/components/themes/roundedraff/RoundedRaffTheme.h:46-81`). UI scale also selects the 10- or 12-point body font (`src/components/UIScale.h:15-32`). The authoritative capacity is therefore the formula at `OptionPopup.h:323-343`, not a hard-coded row count. On short landscape layouts the menu pages; on taller portrait layouts more, sometimes all, rows fit.

Buttons move one item on release and one visible page on continuous input (`OptionPopup.h:198-229`). Touch swipe moves by the current visible count and clamps at either end (`:183-195`); tapping selects only a currently visible hitbox (`:119-179`). Selection changes invalidate layout, so the window recenters and the scrollbar updates. This is sufficient for every row in both orientations, provided Task 10e uses the existing `OptionPopup::processRender()` path so button hints and popup drawing remain paired (`:249-263`).

**Ruling:** keep `OptionPopup`; build the required stable 16-entry action model and pass all 16 labels in one call. Do not add a duplicate capacity constant. A small simulator-only/read-only layout seam may expose `firstOptionIndex` and visible count for tests, but production paging remains owned by `OptionPopup`.

Focused tests:

- Supply 16 uniquely identified rows under 480x800 and 800x480, both UI scales, each shipped theme, and touch on/off. Walk single-step buttons from 0 through 15 and back; hold for page movement; verify every selected action retains its enum identity.
- Swipe until both ends on touch profiles, tap the first and last visible hitbox after each window shift, and assert no stale hitbox selects a prior window's row.
- Use a wrapped/localized title to reduce capacity and prove draw and touch windows still agree. Exercise rotation while the popup is closed and reopen in the new orientation.

## Manga-filtered settings needs one narrow injection seam

The reusable data and widgets exist, but the current reader activity API cannot express the required filter. `SettingInfo` already models toggles, enums, values, actions and submenus (`src/activities/settings/SettingsActivity.h:18-145`), and `addSettingByName()` can copy chosen catalog entries (`src/SettingsList.h:1126-1133`). `ReaderOptionsActivity` already owns the shared FreeInkUI list, scrolling, touch routing, option popup, dirty persistence, and child return behavior (`src/activities/reader/ReaderOptionsActivity.h:27-86`; `src/activities/reader/ReaderOptionsActivity.cpp:546-620`).

Its constructor has no list/filter parameter (`ReaderOptionsActivity.h:88-122`), however, and `rebuildSettingsList()` always calls `buildBookReaderSettingsParentList()`, adds render mode, and constructs font/page-layout/margin/dictionary submenus (`ReaderOptionsActivity.cpp:80-115`). The parent builder contains EPUB-only status, styling, image, bionic, guide, dictionary and indexing controls (`src/SettingsList.h:1135-1160`). Launching it unchanged would violate the binding manga filter.

**Ruling:** add a narrow mode or non-owning builder callback to `ReaderOptionsActivity` that selects a manga list from the existing `getSettingsList()` catalog, while retaining its existing UI, persistence, and scrolling. Prefer a small `ReaderSettingsScope::{Book,Manga}` value over passing a heap-owning `std::function`. In Manga scope, build only catalog entries proven to be consumed by manga/global reader input. At minimum that includes `STR_DISABLE_TOUCHSCREEN`, whose catalog entry is at `SettingsList.h:687-690` and whose global reader-input gate is at `src/main.cpp:1517-1518`. Applicable mapped-input controls should reuse the existing controls list builders rather than copying enum catalogs; those builders begin at `SettingsList.h:1229-1258`. The implementation brief must name the exact included controls after checking that their dispatched actions reach Manga. Panels Only, panel rotation, and orientation stay in the manga menu as required.

Do not use `SettingsActivity`: its public constructor only selects the full settings application (`src/activities/settings/SettingsActivity.h:327-334`), and its rebuild owns every settings category (`src/activities/settings/SettingsActivity.cpp:259-284`). Do not use the current `buildBookReaderSettingsParentList()` and erase unwanted rows afterward; its submenu construction and render-mode insertion make omission fragile.

Focused tests:

- Assert the Manga scope's exact `StrId`/action list and that every included setting has a demonstrated Manga/global-input consumer. Assert all exclusions from the Task 10e brief are absent.
- Toggle each included setting through the real shared row/event code, persist once on exit, return to Manga, and verify page, panel, Panels Only, panel rotation, and orientation are unchanged.
- Exercise touch and buttons, list scroll, child option popup return, allocation failure at activity creation, and prefetch quiesce/resume around the child.

## QR payload ownership and allocation boundary

Current ownership is unsafe under the C3 OOM contract. `QrDisplayActivity` takes `const std::string&` and copies it into a member (`src/activities/reader/QrDisplayActivity.h:8-21`). The existing EPUB caller first grows an unbounded `fullText`, then allocates the child with throwing `std::make_unique`, causing another payload allocation (`src/activities/reader/EpubReaderActivity.cpp:3487-3507`). `Activity::startActivityForResult()` and `ActivityManager::pushActivity()` do preserve the child and its member across launch by moving `unique_ptr` ownership (`src/activities/Activity.cpp:17-20`; `src/activities/ActivityManager.cpp:612-622`), so lifetime is sound after successful construction; allocation failure is not.

`QrUtils::drawQrCode()` adds two more risks. For input over 2,953 bytes it creates a second `std::string` with `substr()`, and it allocates the module grid with throwing `std::make_unique<uint8_t[]>` (`src/util/QrUtils.cpp:11-40`). At version 40 the grid is `ceil(177*177/8) = 3,917` bytes because `qrcode_getBufferSize()` uses `(size*size+7)/8` (`.pio/libdeps/default/QRCode/src/qrcode.c:185-190`, `:770-772`). The codec does not heap-allocate internally, but `qrcode_initBytes()` creates two runtime-sized stack arrays: 3,706 bytes of codewords from the version-40 29,648 raw modules and another 3,917-byte function grid (`qrcode.c:58-70`, `:774-819`). The QR render runs on the reader render task, configured for a 16,384-byte stack (`src/main.cpp:319-320`, `:992`; `src/activities/ActivityManager.cpp:133`). This stack use may fit that configured task, but it must be included in C3 watermark acceptance and must not be duplicated by another framebuffer or large caller-local buffer.

**Required ownership contract:** build at most 2,953 UTF-8 bytes before child creation into one fallibly allocated, NUL-terminated owned buffer (`makeUniqueNoThrow<char[]>(2954)` or a smaller exact allocation after a bounded sizing pass). Return `{owned bytes, uint16_t length, truncated}` or failure. Append OCR blocks directly with explicit remaining capacity and UTF-8 boundary truncation; never create an intermediate page-sized `std::string`. Move this buffer into a fallibly allocated `QrDisplayActivity`; the activity stores `unique_ptr<char[]>` plus length, so the payload survives the stacked child lifetime with no copy. `makeUniqueNoThrow` is the established non-aborting allocator (`lib/Memory/Memory.h:15-40`). Empty and malformed input must fail before launch with the Task 10e messages.

**Required renderer contract:** change `QrUtils` to accept pointer/length (or a view plus an explicitly guaranteed terminator), reject lengths above 2,953, allocate the 3,917-byte module grid with `makeUniqueNoThrow`, and return `bool`/an error enum so `QrDisplayActivity` can render an error instead of claiming a QR was drawn. Use `qrcode_initBytes()` (`.pio/libdeps/default/QRCode/src/qrcode.h:81-85`) to avoid `strlen()` and eliminate the truncation string; its length parameter is `uint16_t`, safely covering 2,953 bytes. The API currently also serves three network-screen call sites (`src/activities/network/CrossPointWebServerActivity.cpp:512`, `:530`, `:550`), so retain a small checked overload if needed, but route all sites through the same fallible core.

The codec's two large stack arrays are a concrete residual risk. The smallest Task 10e choice is to retain the pinned library, document the 7,623-byte version-40 peak, and gate acceptance on render-task high-water measurements on C3 and S3. If the measured margin is inadequate, the bounded fallback is to reject the QR launch/render with a visible memory error; moving those arrays requires changing the third-party codec interface and is outside a narrow menu integration unless hardware evidence makes it necessary.

Focused tests:

- Builder tests cover stored block order, newline insertion, empty input, malformed UTF-8, exact 2,953 bytes, one byte over, and 2/3/4-byte characters crossing the boundary. Assert a terminator exists outside the counted bytes and translation text never enters the payload.
- Inject failure independently for payload allocation, activity allocation, and module-grid allocation. Each path must log, remain/return at the same Manga position, and show the specified error without dereferencing null or invoking a throwing allocation.
- Pass a maximum-size mixed UTF-8 payload through the real `qrcode_initBytes()` path; assert success and stable module output. Test 2,954-byte direct calls are rejected rather than silently copied/truncated.
- Simulator lifecycle test launches the child after the builder's local state is destroyed, forces multiple renders and orientation changes, then returns to the same page/panel. Hardware acceptance records free/largest heap and render-task high-water marks for the 2,953-byte case on C3 and S3.

## Readiness

The 16-row menu is ready on the existing popup and needs no UI redesign. Task 10e implementation should first add the narrow ReaderOptions Manga scope and the owned/fallible QR APIs. Maximum QR rendering remains conditionally ready pending the required C3/S3 stack-watermark evidence; all heap allocations and failure returns can be made bounded within the existing activity and renderer ownership model.
