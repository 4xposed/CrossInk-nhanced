## Concrete gaps beyond the preflight

1. **QR version thresholds are unsafe for UTF-8 byte-mode input.** `src/util/QrUtils.cpp:28-33` selects versions 4/10/20/30/40 using 114/395/1066/2110 boundaries. Pinned `.pio/libdeps/default/QRCode/src/qrcode.c:40-66, :785-798` defines ECC_LOW byte payload capacities of **78/271/858/1732/2953** for those versions (raw whole codewords minus low-ECC codewords minus byte-mode header). `encodeDataCodewords()` (:629-685) and `bb_appendBits()` (:209-217) do not capacity-check; `qrcode_initBytes()` is explicitly preceded by TODO return error for oversized data (:774). Merely switching to initBytes and testing its return code is insufficient. Select safe byte capacities before invoking the codec, and test each threshold with lowercase/multibyte input so numeric/alphanumeric compression cannot hide under-sizing. Keep checked wrapper; do not patch dependency/SDK.

2. **Known QR stack array total is at least 11,359 bytes, not 7,623.** The preflight correctly counts caller arrays at v40: codewordBytes 3,706 and isFunctionGridBytes 3,917 (`qrcode.c:793, :818`). But `performErrorCorrection()` allocates nested `result[data->capacityBytes]` = 3,706 (:709) and `coeff[blockEccLen]` = 30 for ECC_LOW (:712), while both caller arrays remain live. Their sum is 11,359 before ordinary locals, call frames, alignment, and renderer callers. The configured render stack remains 16,384. No build/stack measurement was authorized or performed; physical C3/S3 watermark remains required. This corrects the preflight's concrete accounting without asserting overflow or sufficient margin.

3. **Cache-delete durable stats gate needs an idempotent API.** `MangaReaderActivity::commitReadingStats()` (:738-769) returns void, ignores the `saveReadingStatsWithRetry()` result, and adds `sessionReadingMs` into totals without consuming it. `onExit()` calls it (:125). A new pre-delete call followed by success/Home/exit would bank the session twice; failure also cannot gate deletion. Refactor narrowly to bank once and retain frozen save result/span across retries, return success, and let exit retry pending persistence without re-adding counters. `ReadingStatsSave.h:6-20` already provides the save-result contract. This is necessary to implement the brief's save-before-delete requirement safely, not unrelated stats cleanup.

4. **Shared controls builders are broader than supported Manga settings.** `ReaderOptionsActivity::setCurrentSettings()/activeSubmenuTitleId()` handle only existing font/layout/margin submenus; `toggleCurrentSetting()` (:499-523) does not implement Controls/QuickActions/remap actions. Passing entire controls parent/front/side builders introduces dead actions and font/chapter settings with no manga consumers. Reuse builders to select only supported ordinary rows, or explicitly add narrow handlers if needed; do not expose their unsupported entries. Manga scope should also bypass dictionary discovery at `ReaderOptionsActivity.cpp:69` and font/registry work at :85-90, since the filtered UI does not need either.

## Stats retry continuation: fixed activity-local state and transitions

Requested by root after prep acceptance. Read-only source tracing confirms `saveReadingStatsWithRetry()` (`ReadingStatsSave.cpp:4-21`) accepts a per-target result and attempts only false targets, with one immediate retry per failed target per invocation. Publication appends the supplied language/day span against the current durable source, so a successful target must never receive the same frozen span twice. `setBookCompleted()` (`MangaReaderActivity.cpp:770-782`) also writes stats today and must join the same ordering discipline while a pending transaction exists.

**State (fixed capacity, no queue):** retain existing live `stats` and `globalStats`; add one inline `PendingStatsCommit { frozenBook, frozenGlobal, frozenSpan, saved, active }` member, plus `bankedThroughSeconds`, `activationSessionCounted`, `liveDirty`, `incrementalCommitMode`, and `persistenceFailed`. Both stats structs contain bounded arrays/scalars only (`BookReadingStats.h:10-27`, `GlobalReadingStats.h:10-23`); an inline snapshot pair avoids a new fallible heap allocation and large caller-local stack copy. Establish a modest compile-time size bound for this member after measuring sizeof (expected hundreds of bytes, not file-size buffers; global already asserts <256). Only one transaction may be active. Existing sessionReadingMs becomes explicitly the monotonic accepted active milliseconds for this activation, never cleared during intermediate commits. `bankedThroughSeconds` is the consumption cursor; new fractional milliseconds stay in sessionReadingMs and are not silently rounded away at each attempt.

**Banking once:** with no pending transaction, pause/bank the current running interval into sessionReadingMs. Let A=floor(sessionReadingMs/1000), B=bankedThroughSeconds. Before this activation reaches 10 seconds, retain B=0 and defer time banking exactly as existing threshold policy; after activation qualifies, bank only A-B (including a later tail shorter than 10 seconds). Add that delta once to live total/language/time buckets. The new span starts at activation's original localStart advanced by B seconds using existing `addSecondsToReadingStatsDateTime()` (`ReadingStatsUtils.cpp:147`), has delta seconds, and uses the immutable book language. This preserves the current activity's active-duration attribution model rather than inventing a different pause/calendar policy. Set B=A when banking into the frozen transaction, not on every target's success. Thresholds for one session (60 seconds) and start date (120 seconds) use cumulative A; `activationSessionCounted` prevents any later commit in this activation from incrementing book/global session counters again. Copy the updated live stats and span into Pending, reset Pending.saved to false/false, mark active, and clear liveDirty. A page/completion-only change may create a zero-second/no-span snapshot.

**Frozen transaction is immutable:** call `saveReadingStatsWithRetry(path, frozenBook, frozenGlobal, &frozenSpan, saved)` and retain returned saved bits. If either remains false, leave the snapshot/span/cursor unchanged. Return false to the cache-delete caller, report the failure and resume the same manga view. `recordCurrentPageReadingTime()` keeps accumulating accepted new milliseconds in A; `recordForwardPageTurn()` and completion changes update live stats and set liveDirty. They must not mutate Pending, reset its saved bits, or publish live data behind it. In particular, route the existing direct `setBookCompleted()` save through this state; completion changes can accumulate while the older snapshot is awaiting its failed target.

**One later explicit attempt:** pause accounting once at entry so the attempt operates against a fixed accepted-time boundary. First retry the active transaction's false targets only. If it fails again, stop; do not bank/replace the unconsumed tail and do not launch deletion/exit. If both targets succeed, retire Pending. Then, if A>B or liveDirty or a newly crossed activation threshold requires a change, bank/freeze the next transaction from current live stats and only the unbanked span, and attempt both targets with the existing one-immediate-retry helper. A success on the previous transaction is not replayed; these are new cumulative snapshots carrying only the new delta span. Because input/accounting is paused for the whole attempt, at most two transactions are attempted: previously frozen transaction, then one accumulated tail. Failure of that tail retains it as the sole Pending transaction. No per-frame background write loop or unbounded collection of spans is added.

**Concrete example:** activation reaches 65 seconds. Transaction T1 banks 65 seconds and session +1. Book succeeds; global fails twice, so saved={true,false}. User resumes and accumulates another 12.5 accepted seconds plus a forward-page event. A later attempt retries only global with T1's original 65-second snapshot/span. If still failing, Book is untouched and the 12.5 seconds remain unbanked. If global succeeds, T1 retires; T2 banks 12 seconds, carries cumulative live totals of 77 seconds and session still +1, and sends only its 12-second span to each target. The 0.5-second remainder remains available for future accepted time. If T2 book succeeds/global fails, retain T2 with {true,false}; never resend T1 or the successful T2 book span. Completing T2 and immediately exiting with no new active interval produces no further span or session increment.

**Managed exit retention is necessary:** onExit returns void and destruction follows it, so onExit alone cannot preserve a failed Pending. Latch incrementalCommitMode when the reader first enters the cache-delete precommit path, before creating T1. For the rest of that activation, `prepareToSuspend()` first pauses accounting and drains workers with existing semantics, then runs the bounded flush above before allowing any managed transition/sleep that could discard the activity. A worker still draining returns false with `cancelSuspensionOnFailure()==false`. A completed drain followed by persistence failure returns false with `cancelSuspensionOnFailure()==true`, using Task10b's existing cancellation contract; restore suspended/timer/UI appropriately on cancellation and retain Pending plus the unbanked tail in the reader. Prevent automatic sleep while a failed pending persistence transaction remains, so persistent SD failure cannot trigger a tight repeat of sleep-save attempts. Retry only on a later explicit save/departure request. This applies even if a prior T1 has succeeded but new time has accrued, since the mode stays latched. Temporary child launches may consequently flush the current bounded tail in this mode; they do not create a new activation/session.

Normal managed onExit after a successful gate is idempotent: no active timer, no pending transaction, no dirty snapshot and no new bankable delta means no write. A successful cache delete keeps accounting paused through feedback/Home, so its final onExit has nothing to bank. Outside incrementalCommitMode, preserve the existing exit-save policy while using the same banking-once helper; this task does not create a durable queue. Forced destruction outside the managed preparation contract or power loss cannot guarantee retention of RAM-only pending work. If forced teardown is reachable, log failed targets and unbanked duration explicitly rather than silently claiming persistence; do not equate that unavoidable boundary with a successful managed exit.

**Required focused tests:** (1) T1 book success/global fail, resume+read+page/completion change, global retry success, T2 both success, onExit: exact span totals, one session, no duplicate successful writes; (2) global fails again after resumed reading: frozen snapshot byte-identical and tail untouched; (3) T1 finishes then T2 fails one target: retry only that T2 target; (4) reverse book/global failure roles; (5) both fail then one succeeds then final success; (6) activation reaches 10/60/120-second thresholds across intermediate commits, including sub-10-second eligible tails and millisecond carry; (7) completion mutation while pending cannot bypass ordering; (8) prefetch Draining versus persistence Failed distinguish cancelSuspensionOnFailure; (9) attempted managed exit after repeated failure is cancelled, reading can resume, and later exit succeeds without loss/replay; (10) cache success->Home->onExit performs no duplicate save/span/session. Inject allocation-free fake saves with argument copies/call counts and verify real save helper's one immediate retry contract remains unchanged.
