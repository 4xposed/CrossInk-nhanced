## Geometry limitation requiring an explicit policy

`MangaReaderActivity.cpp:549` temporarily rotates the renderer for image aspect, fits using actual oriented bezel bounds at `:560`, and retains imageOrientation/imageGeometry. OCR rectangles are in the metadata page coordinate system; panel crops are a different coordinate system.

`tools/manga_convert/convert_manga.py:1289` accepts arbitrary panel margins (default 10). At `:1459` it expands/clamps a panel box, crops from the original-resolution image, then resizes the crop at `:1478`. At `:1516` it maps OCR back to page coordinates using the expanded crop; at `:1526` it still serializes the original unexpanded panel box. v2 stores neither the expanded crop origin nor its extent. Consequently arbitrary legacy crop geometry cannot be reconstructed exactly from panel.box plus crop pixel dimensions. Assuming panel.box is the crop produces shifted/scaled highlights. The earlier upstream OCR endpoint/origin bug adds a separate ambiguity for old books (approved design:85).

Recommended compact first implementation: retain exact highlights against the full-page image for overview; when entering lookup from a panel with unproven crop geometry, render that full-page image as lookup background and highlight its panel's OCR blocks there. If no overview image exists, show ordered OCR text with selection rectangles in its own rendered text area; do not fabricate image rectangles. Preserve the original panel and image orientation on exit. Document this legacy limitation. If exact panel-crop overlays are required as Task 9 acceptance, add an optional, versioned converter sidecar containing page-space crop rectangles and source identity; this is a separate concrete format/converter subtask, not something v2 already supplies.

When geometry is known: intersect OCR box with the page/crop extent using wide arithmetic; subtract crop origin; scale endpoints into imageGeometry; transform all four rectangle corners from imageOrientation through physical framebuffer coordinates into the base lookup orientation, then take bounds and clip to the usable viewport. Use the same actual fit result for fresh and cached images. Floor minima/ceil maxima; reject zero/overflowed extents. Never use panel.box as crop extent unless proven. Existing data has block rectangles, not glyph boxes: highlight the whole corresponding OCR block for a selected candidate, and expose the selected word in text. Dividing a block into equal character widths is not exact for Japanese vertical/multiline OCR.

## Dictionary identity issue found during audit

Preserving `engine.signature()` is necessary but insufficient to claim all source/dictionary changes invalidate scans. `StarDictBackend.cpp:61` fingerprints only first/last 256 bytes of idx and dict plus path/sizes/metadata. `lib/Dict/DictIndex.cpp:511` fingerprints only first/last 256 bytes of each Japanese index plus path/size; dictionary bodies are not included there. Same-size middle index edits can change candidates without changing either signature. This is a pre-existing gap, not fixed by Task 9 source adapters.

Add regression cases with files larger than 512 bytes and mutations exclusively in the middle. To meet the strict no-stale requirement, use a validated content identity for every lookup-affecting source (all active Japanese indexes, StarDict indexes and relevant metadata/definitions); an install-generation manifest is safe only if every dictionary replacement/update path maintains it and arbitrary SD edits are detected. The conservative fallback is bounded streaming full-file hashing on dictionary open, cancellable and outside RenderLock. It needs measured latency on real dictionary sizes and a policy for not blocking first definition; sampled hashes plus size/mtime do not prove arbitrary change detection. Do not claim this gap solved or silently expand the manga adapter into replacement dictionary work. Track this as a distinct shared-backend fix/test before strict cache acceptance.

## Follow-up: candidate identity, activation cost, and precise API boundary

This section narrows the earlier conservative fingerprint recommendation. **Do not hash 100 MB definition bodies to validate a candidate-only scan.** A stored PageWordCandidate contains glyph positions/lengths and source ordinals, not a definition, dictionary offset, headword or definition handle. Definitions are looked up/loaded again on every selection.

### Files that actually affect candidates

- **Japanese:** full bytes of each active vocab/JMdict, grammar, and names/JMnedict `.idx`; resolved source path and source-kind/availability mask; companion `.dat` availability and byte size. `DictIndex.cpp:232` opens both files; `:173` validates every index record's offset/length against datSize. `probeExact(:609)` reads only ranked index siblings, never definition bytes. Thus same-size body replacement does not invalidate candidates, but deletion/truncation can. Full index hashing catches same-size middle headword, priority and POS edits. Names/grammar installation, removal and path-precedence changes need invalidation. Deinflection rules and scanner filters live in firmware; mix an explicit candidate-policy version into the identity.
- **Japanese accelerators:** `.spx` is intended to change only speed: `findMatch` at `DictIndex.cpp:407` retries full binary search on narrowed NotFound. Full-index identity plus datSize is sufficient for successful candidates with healthy accelerators. An accelerator I/O failure may make a cold scan fail instead of complete; fingerprint optional sparse sidecars as well if cache reuse must expose changed/corrupt accelerator state. Do not treat hashing a bad sidecar as validation of its semantics.
- **StarDict:** `PageWordScanner.cpp:328` stores the identical source token candidate on both Found and NotFound, with matchedBytes equal to the original token length. It does not persist transformed/alternate results. Therefore a complete successful StarDict candidate array is source-token-dependent, not dictionary-content-dependent. Dictionary replacement can change definitions/suggestions, which are reloaded, but cannot change those stored candidate positions. Errors during probing still prevent publishing a complete scan.
- For the product requirement that changing the selected dictionary invalidates scans anyway, use a conservative StarDict scan identity over resolved path/backend, full `.ifo`, `.idx`, optional `.syn`, presence/size of `.dict`, and candidate-policy version. `.ifo` contains `idxoffsetbits` used by `Dictionary.cpp:779`; `.syn` participates through `StarDictBackend::locate(:157)` and `Dictionary::resolveAltForm(:1055)`. No `.dict` content digest is needed for candidate validity. If retaining the broader existing signature semantics, keep its cheap definition-edge samples, but do not claim they detect all definition edits.
- StarDict search also reads `.idx.oft.cspt`, `.idx.oft`, generated quick-index sidecars and synonym counterparts (`Dictionary.cpp:789`, `:629`). These are not currently uniformly validated against complete source identity. Including their bytes/presence in conservative identity catches sidecar replacement; a separate accelerator-coherence fix would be needed to guarantee correct *fresh* search results after an index rewrite retaining stale sidecars. That is distinct from candidate-cache identity. The minimal source-only StarDict candidate contract avoids conflating these concerns.
- Resolved dictionary paths capture the relevant result of per-book/global `dictionary.bin` and session overrides (`Dictionary.cpp:127`). Hashing unrelated routing-file contents is unnecessary when they resolve to the same backend/path. Japanese per-book ruby glossary influences displayed reading (`JapaneseDictionaryBackend.cpp:41`), not probe candidates; exclude it from scan identity.

### Existing activation/memoization and lock facts

`DictionaryEngine::open(:46)` closes the old backend; StarDict open computes sampled signature synchronously (`StarDictBackend.cpp:84`), and Japanese open calls `DictIndex::open(:554)`, which recomputes its sampled signature. `signature()` is then an O(1) field read until close clears it. There is **no content-identity memo across opens**.

Lookup activity calls open at initial `onEnter(:362)`, suggestion return (`:1035`), dictionary picker success/cancel/failure (`:1107–1141`), and `reopenCancelledEngine(:252)`. In particular `CancelAndJoin` at `:703` closes/reopens at `:715` while replacing an in-flight selection. Putting full-index hashing unconditionally inside backend open would turn rapid cursor movement into repeated multi-megabyte reads. A full-hash fix must not do that.

The inspected opens are outside activity RenderLock scopes; ActivityManager explicitly unlocks before onEnter (`ActivityManager.cpp:304`). But they run synchronously on the main task. A synchronous hash loop that calls yield still prevents that activity's loop from processing Back; adding cancellation checks alone is not user-cancellable. Current Japanese index status has no Cancelled and `DictIndex::open()` has no callback. Avoid silently modifying dictionary lookup semantics to manufacture cancellation.

### Minimal safe scheme for the separate fix

Keep `engine.signature()` and its existing tests/API as the cheap backend-session identity. Add a **separate scan identity operation**, used only for page/OCR scans, with a domain/version tag, full relevant indexes, dat presence/size, and backend/source descriptors as above. No full definition-body reads, global static cache or persistent trust in size/mtime.

Own the verified scan digest in the lookup activity's activation state and retain it across internal cancel/reopen and nested definition transitions only while the same routed source descriptor remains active. Invalidate on dictionary selection/route change, activity exit, transfer/storage mutation boundary or source availability/size change. Recompute on each new lookup activity; a path+size+mtime memo across arbitrary SD replacements is not proof of unchanged middle bytes. Arbitrary external mutation *during* one active lookup cannot be guaranteed detectable by any once-per-activation digest; existing index/definition caches already assume an immutable active session. State that session boundary explicitly. If truly concurrent file transfer is allowed, coordinate it or invalidate/cancel the session before mutation.

Perform full-index identity incrementally in the foreground outside RenderLock, using one existing/bounded heap scratch buffer and explicit per-step byte budget, before trusting a persisted scan. A small `beginScanIdentity/stepScanIdentity/cancelScanIdentity` backend operation can read the already-open Japanese index handle (avoiding a forbidden second reader) when no worker/probe owns the engine; StarDict can open/close one index file per step/session. Each step returns Pending/Ready/Unavailable/ReadError/Cancelled and never changes the public definition lookup result. Publish the digest only after all reads succeed. Hash read failure should disable scan-cache load/save and fall back to ordinary scanning, rather than making a usable dictionary unavailable. Retain identity across the internal engine reopen via explicit activity-owned context; do not permit backend close to erase the activation digest accidentally.

This is a small orchestration addition, not a zero-behavior-change one: a cold full index costs I/O before a warm scan can be trusted. Measure that cost. If it exceeds the opening budget, allow the activity to abandon cache verification for that activation and use normal progressive scanning (do not load/save an unverified cache). Do not run hashing concurrently against dictionary probes or renderer file reads. Hashing indexes once per top-level lookup is safe for candidate identity and much smaller than bodies, but large names indexes can still be expensive; no timing promise is justified without measurements. A persistent install-generation manifest is a future optimization only if all SD dictionary mutations become reliably tracked.

### Concrete OCR/shared-activity API proposal for the next brief

Prefer a small movable value owner over a virtual source class:

```cpp
struct OwnedLookupTextSource {
  std::unique_ptr<PageTextGlyph[]> glyphs;
  uint16_t glyphCount = 0;
  uint32_t contentHash = 0;
  bool truncated = false;
  PageTextSourceView view() const;
};

// In MangaPageTextSource: length-aware two-pass build, fallible owned output.
DictionaryStatus buildMangaLookupTextSource(
    manga::format::PageView page, int16_t panel,
    const MangaLookupGeometry& geometry, OwnedLookupTextSource& out);

// Additional overload; keep both existing constructors intact.
EpubReaderWordLookupActivity(GfxRenderer&, MappedInputManager&,
                             OwnedLookupTextSource, EpubLookupPageRequest);
```

`MangaLookupGeometry` is a proposed small by-value snapshot of source extent, image fit, image/base orientations and explicit geometry-known/fallback mode; do not infer crop origin from panel.box. Add an optional owned `scanCacheFilePath` to the request, retaining `/wlscan.bin` as EPUB default. Add private `sourceView()`, `sourceTruncated()`, `clearSource()` and a source-kind tag (`EpubPage`, `External`) to the activity; change only source accesses, page initialization/reload and external ownership clearing. Dictionary switching reuses immutable external glyphs and restarts the scanner; it must not rebuild a Page. Existing render callback handles background and font switching.

The manga parent retains a compact snapshot mapping source-word ordinals to OCR block/byte ranges for returned clipping; this snapshot must survive child teardown because the child clears source before publishing DictionaryClippingRequest. Alternatively reconstruct the mapping from an immutable parent PageView after result, before any reload. Preserve the ordinal policy between builder and result consumer in one tested helper. The proposed glyph owner cannot reconstruct clipped source bytes after it has been freed, so returning existing byte offsets without this parent mapping is incomplete.
