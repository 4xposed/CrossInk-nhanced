## Proposed small API and state

Add a distinct `DictionaryScanIdentityStatus { Pending, Ready, Unavailable, ReadError, OutOfMemory, Cancelled }`, plus a move-only `DictionaryScanIdentityState` owned by the lookup activity. Proposed engine API:

```cpp
DictionaryScanIdentityStatus beginScanIdentity(DictionaryScanIdentityState& state);
DictionaryScanIdentityStatus stepScanIdentity(DictionaryScanIdentityState& state, size_t byteBudget);
bool resumeScanIdentity(DictionaryScanIdentityState& state); // descriptor check after same-activation reopen
void cancelScanIdentity(DictionaryScanIdentityState& state);
```

State holds: status, private rolling hash, published digest (zero/unusable until Ready), source ordinal, byte offset, and the activation's resolved route descriptor. It contains no file handle, renderer pointer, worker or persistent/global memo. Keep cursor/hash fields fixed-size; use an explicitly bounded owned StarDict base path only if necessary to compare the exact route across reopen. Japanese route descriptors can use the fixed path-table selections, active-source mask and captured index/data extents. Do not use only book language or sampled `signature()` to decide route equality. Canonically serialize tags/lengths/sizes in a specified byte order; add a scan-policy domain/version tag. Continue using the existing uint64 cache field for the new full-stream digest; it is a content fingerprint, not a cryptographic integrity guarantee.

`begin` captures descriptors and seeds state without streaming payloads; metadata discovery can itself be a bounded Pending phase. `step` performs at most one bounded read (initially 256 bytes) and bounded descriptor transitions, checks cancellation before/after it, and publishes Ready only after all expected bytes have been read successfully. A single slow SD read is not time-preemptible: the byte bound controls work, not a promised wall-clock latency. Avoid creating an additional large buffer: reuse Japanese `DictIndex::Impl::signatureScratch` (`DictIndex.cpp:547`, 256 bytes), and StarDict's existing `plainBuffer_` (`StarDictBackend.cpp:102`, 512 bytes) only under the exclusive scheduling contract. No new stack buffer larger than 256 bytes.

Backend dispatch remains below DictionaryEngine. Japanese implementation belongs inside DictIndex because `SourceState` is private (`DictIndex.cpp:58`): read each **already-open** `idxFile` with explicit offset/length using `readExact(:126)`, never reopen the same index path. Searches also seek explicitly, so a hash slice may change file position without invalidating block-cache contents. Data handles remain open but only their captured size/presence is included (`openSource():232–255`). StarDict searches create and close local lookup sessions (`Dictionary.cpp:772,930–938,945–966`): open/seek/read/close the selected identity file within each step. Do not retain that extra handle across a probe, definition worker or engine close. Close explicitly on every error/cancel path.

Hash these inputs:

- Japanese: active vocab/grammar/names source IDs, exact resolved index/data paths, availability and extents, **all bytes of each active index** (keys, definition offsets/lengths, priority and POS). No `.dat` payload; ruby glossary is excluded because it does not change candidates.
- StarDict: exact resolved base path, full `.idx`, optional `.syn`, full `.ifo` (including offset width/type interpretation), relevant parsed descriptors and `.dict` availability/size. File suffixes are defined in `Dictionary.h:9–23`. Optional canonical-source absence is encoded distinctly; unreadable present canonical files disable verification. Do not read `.dict`/`.dat` bodies for this operation.
- **Exclude derived accelerators, including presence/size, from both digest and activation route descriptor:** `.qidx`, `.idx.oft`, `.syn.oft`, `.idx.oft.cspt`, `.syn.oft.cspt` and Japanese `.spx`. None is an authored semantic dictionary input. `Dictionary::buildQuickIndex` (`Dictionary.cpp:421–481`) derives sparse byte offsets from `.idx`; `prepareQuickIndex(:506–531)` can create/replace it during lookup. `scripts/dictionary_tools.py:29,59` derives `.oft`/`.cspt` from index/synonym bytes, and `scripts/gen_dict_spx.py:22–33` derives `.spx` keys from fixed-stride `.idx` records (also `tools/dict_convert/convert_jmdict.py:186–188`). Generation can legitimately change accelerator files mid-activation without changing the dictionary. Canonical full-index hashing already detects dictionary edits. Stale/malformed accelerator coherence can affect fresh searches, but hashing the accelerator would not repair that issue; retain it as a separate existing concern, not a new 9c invalidation trigger or I/O cost.

## Scheduling and responsiveness

1. Start an empty activation identity for page/OCR mode after successful initial routing. Direct-word mode has no page scan cache and needs no full identity. Build the source and initialize progressive scanning immediately; do not synchronously stream indexes in backend `open()` or `onEnter()`.
2. After input is handled, allow one bounded initial identity slice before the first scanner step: at most 16 steps of 256 bytes, stopping at a cooperative 5 ms elapsed limit and checking cancellation between steps. This permits a real small multi-file dictionary to finish; a single read alone would systematically bypass even tiny multi-file caches. One slow SD read can exceed the elapsed limit. If verification completes and no scan/candidate/selection has started, attempt a validated cache load and restore its cursor normally. Otherwise latch `cacheLoadBypassed = true` as soon as progressive scanning starts. No repeated verification-first opening delay and no late replacement of the candidate array/cursor. Test a real small dictionary's second-activation cache load, not only a mocked Ready state. For large indexes, strict validation may finish after progressive scanning and make persistent caches unhelpful on that activation; report this tradeoff separately from first-definition latency.
3. Prioritize `runScanSlice()` and all queued lookup/definition/prewarm commands. While the first definition is loading (or touch initial selection is unresolved), defer further identity I/O. Once definition Ready/NotFound is available, or scanning is complete with no selection, spend at most one identity chunk per eligible main-loop turn. If scanning uses the entire existing 50 ms allowance, skip that turn's hash chunk. **Extend `skipLoopDelay()` (`EpubReaderWordLookupActivity.cpp:927`) with the same `identityStepEligible()` predicate**, which requires Pending, an open matching engine, no initial-definition/touch priority, no exit and no flow/actual worker ownership. This selects the existing `yield()` path in `main.cpp:1666–1676`, avoiding a mandatory 10/50 ms delay per 256 bytes. Input is polled on every turn; the RTOS is yielded after every chunk; no unbounded inner hashing loop is introduced. The identity branch must become false immediately on Ready/error/cancel, priority work or other-worker ownership, so Pending-but-ineligible state does not create a new busy-spin reason (existing worker-related delay policy remains unchanged). A future measured optimization may use a bounded multichunk slice, but is unnecessary for the initial scheduling contract. Throughput still depends on SD seeks/reads and other work; do not promise a completion time for the user's roughly 76 MiB indexes. On later eligible turns verification can finish and make a completed, untruncated live scan eligible for saving. Do not discard a Pending verification simply because warm-cache loading was bypassed.
4. Identity never runs on the dictionary worker and never overlaps scanner probes or definition work. In particular, recheck worker ownership after `runScanSlice()` because it may have launched a job. Check `exiting_`, engine availability, Pending status and command/selection state before every step.
5. The audit explicitly says, “Do not run hashing concurrently against dictionary probes or renderer file reads” (`2026-09-06-manga-ocr-audit.md:101`). Existing HAL serialization already excludes simultaneous physical storage reads: `HalStorage::StorageLock` takes SPI/storage locks (`lib/hal/HalStorage.cpp:186–189`), and `HalFile::read` uses that wrapper (`:410,429`). Retain normal HAL I/O rather than adding the previously proposed render-deferral flags. Renderer and hash calls may interleave, but their physical reads are serialized; renderer fonts/background use different file handles and do not access the backend's identity scratch. The separate worker/probe exclusion remains essential because those operations share backend handles/buffers. Hashing must never draw, touch renderer state, bypass HAL, or hold RenderLock. An entire-render exclusion gate would be stricter than the cited read-exclusion requirement and has no demonstrated candidate-correctness need here; leave it out unless hardware evidence establishes such a need. No new renderer/ActivityManager/SDK mechanism is required.

## Activation lifetime and failure semantics

- Keep both Ready digest and Pending offset/hash across internal cursor cancel/reopen, nested definitions, suggestion return and picker cancellation **only when** the reopened backend descriptor exactly matches the activation descriptor. Since state has no borrowed backend handles, a resumed step reads through the new backend at its saved offset. A route/availability/extent mismatch invalidates state and any loaded cache; restart scanning against the new route. Picker success always starts fresh verification; failed selection/restoration may conservatively restart verification.
- New top-level activity, final exit or transfer/storage-mutation boundary discards all trust. No memoization across activations by path/size/mtime. Files are immutable during an active lookup, matching existing dictionary session assumptions. If the product permits concurrent transfer mutation, quiesce lookup before mutation; once-per-activation hashing cannot detect arbitrary in-session external edits.
- Cache load/save require Ready, matching route, nontruncated source and the existing complete/nontruncated scan checks. `cacheLoadBypassed` blocks only load, not a later verified save. Cache absence/corruption remains an ordinary fresh scan.
- Read/seek/OOM/unavailable/cancelled identity results log context and disable cache load/save for that activation, without changing a usable engine's lookup status or clearing its definition. Never publish partial digest, turn identity failure into dictionary-unavailable UI, or finish a hash in an exit callback. Cancel of the overall lookup abandons Pending work immediately; internal worker cancellation alone need not discard the independent resumable identity.
- Sparse-body test counters must be reset **after ordinary engine open**: existing StarDict `signature()` samples `.dict` at `StarDictBackend.cpp:61–80,126`. Preserve that API. The new scan-identity operation must read zero body payload bytes; do not incorrectly claim engine open also does so.
